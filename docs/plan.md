# План: гибрид Syncthing + собственный control plane

> Выбранный вариант: **Syncthing как data plane + наш control plane**, транспорт — прямой
> P2P, при неудаче — **публичный пул community-релеев Syncthing**. TURN не используется.
>
> Связанный документ: [обзор вариантов](README.md).
> Оценки — для команды 4–5 человек; это рабочий план, не финальное ТЗ.

## 0. Резюме

Строим аналог SyncTrayzor, где:

- клиент видит **весь каталог библиотек** сервера (свой crawler, не Syncthing);
- пользователь выбирает папки в клиенте (файл — только вместе с родительской папкой);
- выбор применяется локально через `.stignore` (Syncthing REST API) — сервер не создаёт
  папку под каждого клиента;
- origin отдаёт **одну Syncthing-папку на библиотеку**, расшаренную устройствам с доступом;
- Syncthing синхронизирует только выбранное — напрямую или через community-relay.

**Срок до beta:** 14–16 недель. **Команда:** 1 backend, 1 sync/infra, 1–2 клиентских,
0.5 QA, 0.5 дизайна — 4–5 человек.

**Главные риски:** публичные релеи без SLA; клиент хранит метаданные всей библиотеки;
выбор — это фильтр, а не отдельная шара, поэтому ACL работает на уровне библиотеки.

## 1. Решение и его границы

| Аспект | Как в этом плане |
|---|---|
| Транспорт | Syncthing BEP: TCP/QUIC, при неудаче — relay pool |
| Авторизация | Свой OIDC + привязка Syncthing Device ID |
| TURN | Нет; публичный relay не аутентифицирует и не выдаёт креды |
| Каталог | Crawler библиотек в control plane |
| Выбор | Локальный `.stignore`: папки; файл — только через родителя |
| Серверная настройка | Одна папка на библиотеку; папок под клиента нет |
| ACL | Граница библиотеки; библиотеки не вкладываются друг в друга |
| Placeholders | Нет; «освободить место» удаляет выбранное |
| Версии | Снапшоты library; `.stversions` на sendonly не пополняется |

### Почему не «папка на каждый выбор»

Первая версия плана делала срез (отдельную Syncthing-папку) на каждую выбранную папку.
От этого пришлось отказаться: **Syncthing не поддерживает вложенные шары**. Официальный
FAQ прямо говорит: вложенные папки «not supported, recommended or coded for», с
непредсказуемыми эффектами
([FAQ](https://docs.syncthing.net/users/faq.html#am-i-able-to-nest-shared-folders-in-syncthing)).

Пример: устройство A выбрало `/Фото`, устройство B — `/Фото/2024`. На origin появились
бы две папки с вложенными корнями. Родительская папка включает дочернюю, `.stfolder`
дочерней попадает в родительский скан, а удаление/переименование в одной папке
конфликтует с другой. Для продукта это недопустимый риск.

Поэтому:

- **библиотека** — единственная единица шаринга и ACL;
- библиотеки **не пересекаются** (валидация при создании);
- выбор внутри библиотеки — **фильтр на клиенте**, а не новая папка на сервере.

Плата: клиент получает индекс всей библиотеки (но не данные), а пользователь с доступом
к библиотеке теоретически может снять `.stignore` и скачать всё. Если нужен ACL на
поддерево — это отдельная библиотека (или вариант C).

## 2. Архитектура

```
┌────────────────────────── Клиент ─────────────────────────────┐
│  UI (навигатор) ── local REST ── Syncthing (headless)         │
│       │   выбор папок                  │                       │
│       └── Control API (каталог, доступ)│  BEP: TCP/QUIC       │
└───────────────────────────────────────┼───────────────────────┘
                                        │ fallback: relay pool
┌────────────────────────── Origin ─────┼───────────────────────┐
│  Syncthing (sendonly) ── library      │                       │
│       ▲                               │                       │
│       │ local REST                    │                       │
│  Origin agent ── mTLS ── Control API ─┘                       │
│       │                                                       │
│  Catalog crawler ── PostgreSQL ◄── Control API                │
└───────────────────────────────────────────────────────────────┘
```

### Компоненты

| Компонент | Ответственность |
|---|---|
| **Control API** | OIDC, устройства, библиотеки, каталог, доступ, аудит |
| **PostgreSQL** | пользователи, устройства, origin, библиотеки, узлы каталога |
| **Catalog crawler** | обход библиотек, fsnotify, индексация, поиск |
| **Origin agent** | REST к локальному Syncthing, создание папки библиотеки, шаринг, отзыв |
| **Share manager** | доступ устройств к библиотекам, идемпотентные задания |
| **Syncthing origin** | sendonly-папка на библиотеку, отдача данных |
| **Syncthing client** | receiveonly-папка, `.stignore`, локальный индекс |
| **Relay pool** | `dynamic+https://relays.syncthing.net/endpoint` |
| **Клиентский UI** | дерево, поиск, выбор папок, статусы, настройки |

### Топология

**Звезда:** клиенты синхронизируются только с origin, не друг с другом.

- ACL и отзыв — в одном месте (origin);
- каталог — один crawler на библиотеку;
- нет mesh-сложности и конфликтов между клиентами;
- минус: нет swarm-раздачи; при необходимости — отдельный этап.

## 3. Модель выбора: библиотека + ignore

### Библиотека

Библиотека задаётся администратором:

```json
{
  "id": "lib-photo",
  "origin_id": "origin-1",
  "root_path": "/srv/library/photo",
  "acl": ["team-photo"],
  "exclude": [".stfolder", ".stversions", "*.tmp"]
}
```

- Корни библиотек **не пересекаются**; вложенность отклоняется при создании.
- Одна библиотека = одна Syncthing-папка на origin.
- Устройства с доступом добавляются в папку; клиент создаёт локальную папку с тем же ID.
- Клиент видит только библиотеки, разрешённые ACL; каталог фильтруется на API.

### Выбор

Выбор хранится **на клиенте** (локальная БД) и не отправляется на сервер.
Это приватность и меньше серверного состояния. Опционально позже — шифрованный блоб
настроек для синхронизации между устройствами пользователя.

Правило:

- выбрана папка → скачивается всё её содержимое;
- всё остальное игнорируется;
- исключения внутри выбранного (например, `node_modules`) идут раньше include;
- отдельный файл не выбирается: Syncthing не умеет включить файл, не включив его
  родительскую папку. UI предлагает выбрать родителя.

### Генерация `.stignore`

Используем whitelist-паттерны. Порядок важен: **первое совпадение выигрывает**
([Ignoring Files](https://docs.syncthing.net/users/ignoring.html)).

```text
# 1. Исключения (если есть)
/Фото/2024/private

# 2. Предки выбранных папок — чтобы Syncthing дошёл до них
!/Фото
!/Фото/2024
!/Фото/2024/**
!/Документы
!/Документы/Проект X
!/Документы/Проект X/**

# 3. Всё остальное — игнор
*
```

- Для папки: `!/path` + `!/path/**`.
- Отдельный файл включить нельзя: `!/parent` разворачивается в `!/parent/**` и тянет
  соседей. Это проверено на Syncthing v2.1.7 в e2e-стенде.
- Ведущий `/` обязателен: без него negations заставляют Syncthing обходить весь дерево.
- Спецсимволы экранируются; на Windows — `|` или `#escape=\`.
- Паттерны ставятся через `POST /rest/db/ignores` (не редактируем файл вручную).
- После установки — `POST /rest/db/scan?folder=...` и ожидание `FolderSummary`/`StateChanged`.

Ограничения:

| Параметр | MVP |
|---|---|
| Паттернов на библиотеку | 2000; при превышении просим укрупнить выбор |
| Глубина пути | 32 |
| Выбранных узлов | 5000 |
| Файл | нельзя; выбирается родительская папка |
| Placeholder | нет |

### Состояния выбора

```text
idle → computing → applying_ignores → rescanning → syncing → active
                       ↘ error (revert to previous patterns)
```

- Храним предыдущий набор паттернов; при ошибке откатываем.
- Дебаунс 1–2 с при массовом выборе.
- Статус узла в UI: `remote_only`, `selected_pending`, `selected_syncing`,
  `selected_synced`, `excluded`, `error`.

### «Освободить место»

1. Обновить `.stignore`, исключив путь.
2. Запустить `POST /rest/db/scan` и дождаться `idle`.
3. Удалить локальные файлы.
4. Убедиться, что Syncthing не тянет их обратно.

Если удалить до ignore, `receiveonly` может восстановить файлы с origin.

### Изменения на origin

- Удаление/переименование внутри выбранного — Syncthing разносит как обычно.
- Переименование корня библиотеки — выбор не «переезжает»: путь в паттернах устаревает.
  UI помечает выбранные узлы `missing`, пользователь выбирает заново.
- Ошибка доступа к подкаталогу не роняет библиотеку: узел каталога получает `error`.

### Граница безопасности

Важно проговорить с продуктом: **выбор — это оптимизация трафика, а не ACL**.
Устройство, получившее доступ к библиотеке, может удалить `.stignore` и скачать всю
библиотеку. Если это неприемлемо:

- разбить контент на непересекающиеся библиотеки с разным ACL;
- либо вернуться к варианту C с пофайловым ACL.

## 4. Control plane

### Сервисы

- `api` — REST/SSE для клиента и агентов.
- `identity` — OIDC, устройства, токены, отзыв.
- `catalog` — crawler, поиск, пагинация.
- `share-manager` — доступ устройств к библиотекам, задания, реконсиляция.
- `audit` — кто получил доступ, какие устройства добавлены/удалены.

### Модель данных

| Таблица | Поля |
|---|---|
| `users` | id, email, display_name, status |
| `devices` | id, user_id, syncthing_device_id, platform, pubkey, status, last_seen |
| `origins` | id, name, api_url, agent_cert, status |
| `libraries` | id, origin_id, root_path, acl_scope, state |
| `library_devices` | library_id, device_id, local_path, state, synced_at |
| `nodes` | id, library_id, parent_id, rel_path, kind, size, mtime, deleted_at |
| `jobs` | id, type, payload, state, attempts, run_after |
| `audit` | id, actor, action, object, ts, ip |

Ключевые индексы: `nodes(library_id, parent_id)`, `nodes(library_id, rel_path)`,
`library_devices(device_id)`, `jobs(state, run_after)`.

### API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/auth/device` | привязка Device ID к пользователю |
| GET | `/v1/libraries` | доступные библиотеки |
| GET | `/v1/catalog/{node}` | дети узла, cursor/limit |
| GET | `/v1/catalog/search` | поиск |
| POST | `/v1/devices/{id}/revoke` | отзыв |
| GET | `/v1/events` | SSE: каталог, доступ, статусы |
| внутренние | `/v1/internal/...` | origin agent: jobs, heartbeat |

Выбор **не** отправляется через этот API: клиент применяет его локально.
Опционально — `PUT /v1/devices/{id}/prefs` с шифрованным блобом.

### Провизioning библиотеки

Состояние на пару `(library, device)`:

```text
requested → validating → client_folder_creating → origin_folder_creating
          → sharing → syncing → active
          → paused → removing → removed
                       ↘ error (retry/rollback)
```

- Сначала клиент создаёт локальную папку с origin в списке устройств.
- Затем origin создаёт папку библиотеки (если её ещё нет) и добавляет устройство.
- Одна папка библиотеки обслуживает все устройства; добавление устройства — идемпотентно.
- Reconciliation раз в 60 с сверяет БД с Syncthing origin и клиентом.

### Crawler

- Обходит только `libraries.root_path`.
- Пропускает `.stfolder`, `.stversions`, `.stignore`, `*.syncthing.*.tmp`.
- Хранит имя, путь, тип, размер, mtime; хеши — позже.
- `fsnotify` + дебаунс 2 с; полный reconcile ночью.
- Пакетная запись; keyset-пагинация; ошибки доступа не валят обход.
- Для библиотеки > 1 млн файлов — отдельный лимит/шардирование, см. spike.

### Auth и отзыв

1. OIDC device flow → access/refresh.
2. Клиент регистрирует Syncthing Device ID.
3. Share manager добавляет Device ID в папки библиотек с доступом.
4. Отзыв: удалить из всех библиотек, очистить токены и локальный Syncthing-конфиг.
5. Если устройство офлайн — при следующем коннекте origin его уже не знает.

## 5. Конфигурация Syncthing

### Origin: одна папка на библиотеку

```json
{
  "folders": [{
    "id": "lib-photo",
    "label": "Фото",
    "path": "/srv/library/photo",
    "type": "sendonly",
    "devices": [{"deviceID": "ORIGIN..."}, {"deviceID": "CLIENT-A..."}],
    "fsWatcherEnabled": true,
    "rescanIntervalS": 3600
  }],
  "options": {
    "listenAddress": [
      "tcp://0.0.0.0:22000",
      "quic://0.0.0.0:22000",
      "dynamic+https://relays.syncthing.net/endpoint"
    ],
    "relaysEnabled": true,
    "globalAnnounceEnabled": true,
    "localAnnounceEnabled": true
  }
}
```

- `sendonly` — клиенты не меняют origin.
- Устройства добавляются в `devices`; при большом числе — шардировать origin/библиотеки.
- GUI/API — только `127.0.0.1`; API key в секрете.
- Серверная история — снапшоты library; `.stversions` на sendonly не пополняется.

### Клиент: receiveonly + ignore

```json
{
  "folders": [{
    "id": "lib-photo",
    "label": "Фото",
    "path": "/home/user/Sync/origin/photo",
    "type": "receiveonly",
    "devices": [{"deviceID": "CLIENT-A..."}, {"deviceID": "ORIGIN..."}],
    "fsWatcherEnabled": true
  }]
}
```

- `receiveonly` исключает конфликты от локальных правок в MVP.
- `.stignore` ставится через `POST /rest/db/ignores`.
- Локальный API — на localhost, ключ в OS keychain.
- Клиент не запускает GUI Syncthing.

### Публичный пул

- `dynamic+https://relays.syncthing.net/endpoint` в listen addresses.
- Пул отдаёт 100 случайных релеев из ~1000; клиент меряет latency, сортирует по
  корзинам 50 мс, перемешивает и пробует по очереди
  ([`dynamic.go`](https://github.com/syncthing/syncthing/blob/b0df1033fe2a788cd4f4e606dbb27199eefaf340/lib/relay/client/dynamic.go#L142-L178)).
- Релеи не проверяются проектом; часть ограничивает полосу; трафик E2E-зашифрован,
  релей видит IP, Device ID и объём.
- Порты: 22067/tcp (данные), 22070/tcp (статус); часто 443.

### Свой релей для SLA

```bash
strelaysrv -keys /var/lib/strelaysrv \
  -listen :22067 -ext-address :443 \
  -provided-by "MyOrg" -global-rate 50000000 -per-session-rate 5000000
```

`relay://relay.example.com:443/?id=<Device ID>` в listen addresses. По документации
конкретный `relay://` используется вместо публичного пула — проверить на своей версии.
Приватный: `-pools="" -token=...` и `&token=...` в URL.

## 6. Клиент

### Состав

- Трей-оболочка (Tauri 2 + Rust или .NET/Avalonia).
- Встроенный `syncthing` (headless), отдельный home, pinned версия.
- Локальный агент: запуск, API key, конфиг, создание папок, `.stignore`.
- UI: дерево каталога, список, поиск, tri-state выбор, статусы.
- Локальная БД: кэш каталога, выбранные узлы, предыдущие паттерны.

### UX выбора

- Слева — дерево библиотек; в центре — содержимое; сверху — хлебные крошки и поиск.
- Чекбокс папки; у файлов — disabled с подсказкой «выберите папку».
- Панель: «будет скачано: 12,4 ГБ, 1 842 файла», кнопка «Применить».
- Статусы: `только на сервере`, `в очереди`, `качается`, `синхронизировано`,
  `исключено`, `ошибка`.
- Контекстное меню: «Скачать», «Пауза», «Убрать с устройства», «Освободить место».
- Панель: активные библиотеки, скорость, ошибки, конфликты, история.

### Placeholders

Их нет. Нельзя открыть файл, которого нет локально, без скачивания. Это ограничение
надо явно показать в onboarding и в UI, иначе продукт будут сравнивать с Dropbox.

### Функции SyncTrayzor, которые сохраняем

Автозапуск, трей, уведомления, окно передач, пауза на лимитном трафике, разрешение
конфликтов, portable-режим, локализация.

## 7. План работ

| Этап | Недели | Результат | Gate |
|---|---:|---|---|
| 0. Spike | 1–2 | Одна библиотека расшарена; whitelist `.stignore`; папка и исключение; 1 ГБ через relay; 100k каталог | Go/no-go |
| 1. Control plane core | 3–5 | OIDC, устройства, библиотеки, API каталога, аудит | Логин + каталог |
| 2. Catalog | 4–6 | Crawler, fsnotify, поиск, пагинация | 100k узлов, свежесть < 60 с |
| 3. Client shell | 5–8 | Трей, Syncthing, локальный API, дерево, поиск | Каталог в UI |
| 4. Selection engine | 7–10 | Паттерны, `POST ignores`, rescan, статусы, free space | 10 папок, 3 устройства |
| 5. Lifecycle/security | 9–11 | Отзыв, ACL, лимиты, reconciliation, ошибки | Отозванный не синхронизируется |
| 6. Hardening | 12–13 | Scale, relay outage, сон, диск полон, апгрейды | 100 ГБ, 3 дня soak |
| 7. Beta | 14–16 | Пакеты, автообновление, доки, пилот | SLO и runbooks |

**Статус:** e2e-стенд уже собран в [`syncscope/lab/e2e.py`](../syncscope/lab/e2e.py).
На Syncthing v2.1.7 проверены: шаринг библиотек, выбор папки, исключение внутри неё,
отзыв устройства, free space, живой каталог через fsnotify, UI-навигатор, multi-mount,
OIDC device flow и force-relay через локальный strelaysrv.
Отдельный файл выбрать нельзя — `!/parent` разворачивается в `!/parent/**` и тянет
соседей; это зафиксировано в модели выбора.

**Spike — обязательный gate.** Проверить:

1. Один origin + клиент, одна библиотека, локальная папка через REST.
2. Whitelist `.stignore`: папка, вложенный выбор, исключение внутри выбранного; файл — ожидаемый отказ.
3. «Освободить место»: ignore → scan → delete → файлы не возвращаются.
4. 100k файлов: размер индекса клиента, время скана, память.
5. 1 ГБ через публичный relay: скорость, обрывы, переключение.
6. Если индекс/скан или relay не укладываются — решаем: свой relay, разбиение
   библиотек, либо возврат к варианту C.

10. Runbooks: застрявший доступ, origin недоступен, релей лёг.

### Команда

1 backend (API/Postgres/share manager), 1 sync/infra (Syncthing, agent, relay),
1–2 client (UI + agent), 0.5 QA, 0.5 design. При двух разработчиках — 7–8 месяцев.

## 8. Тестирование и приёмка

| Сценарий | Ожидание |
|---|---|
| Выбор папки | Скачивается только она |
| Выбор файла | UI предлагает родителя; отдельный файл не качается |
| Вложенный выбор | Паттерны не конфликтуют, лишнее не качается |
| Исключение внутри выбранного | Исключено |
| Снятие выбора | Файлы удалены, не возвращаются |
| Переименование на origin | UI `missing`, без порчи данных |
| Case/unicode/спецсимволы | Паттерны корректны |
| Только relay | Синхронизация идёт, UI показывает `relay` |
| Relay оборвался | Переподключение, без потери |
| Отзыв online/offline | Доступ прекращён |
| Клиент снял `.stignore` | Видит всё — это ожидаемое ограничение ACL |
| 100k файлов | Каталог и скан в норме |
| 100 ГБ / 3 дня | Без утечек и зависаний |

### Приёмка MVP

- Пользователь видит весь каталог без ручной настройки origin.
- Выбор папки скачивает только её; снятие освобождает место.
- В UI видно, идёт ли трафик напрямую или через relay.
- Отозванное устройство не синхронизируется.
- Перезапуск компонентов не ломает состояние.
- Нет открытого GUI Syncthing и API key в логах.
- 10 пользователей, 3 origin, 20 библиотек — без деградации.

### SLO

| Метрика | Цель |
|---|---|
| Применение выбора, p95 | < 5 с |
| Первый файл, p95 | < 15 с в LAN |
| Свежесть каталога | < 60 с |
| Ошибки применения паттернов | < 0,5% |
| Доступность control plane | 99,9% |

## 9. Эксплуатация

- Docker Compose: `postgres`, `api`, `share-manager`, `origin-agent`,
  `syncthing-origin`, reverse proxy; Redis/NATS — по необходимости.
- Бэкапы: Postgres ежедневно; конфиг Syncthing; снапшоты библиотек.
- Метрики: доступ, задания, ошибки, relay-соединения, размер индекса.
- Логи: structured JSON, без токенов и API keys.
- Runbooks: добавить origin/библиотеку, ротация ключей, отзыв, застрявший доступ,
  деградация пула.
- Обновления: control plane rolling; Syncthing pinned; миграции на копии БД.

## 10. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Публичные релеи медленные | высокое | свой relay для SLA, direct-first, замер |
| Индекс всей библиотеки тяжёлый | высокое | лимит размера, разбиение библиотек, spike |
| Клиент обходит выбор | высокое | ACL библиотеки; раздельные библиотеки; документация |
| Ошибки ignore-паттернов | высокое | golden-тесты, dry-run, откат |
| Вложенные библиотеки | высокое | валидация при создании |
| Много устройств в папке | среднее | шардирование origin |
| Нет placeholders | среднее | честный onboarding |
| Отзыв не доехал | высокое | удаление из всех библиотек, аудит |
| Windows-пути/регистр | среднее | валидация, long paths, тесты |
| MPL-2.0 | среднее | не модифицировать бинарь, notices |

## 11. Открытые решения

1. ACL: хватает ли библиотеки как границы, или нужны под-библиотеки?
2. Максимальный размер библиотеки (файлов/ТБ) до разбиения?
3. Публичный пул — единственный транспорт или для платных тарифов свой relay?
4. MVP read-only или сразу двусторонний?
5. Windows-only на beta или сразу macOS?
6. Нужны ли placeholders? Если да — гибрид не закрывает, нужен вариант C.
7. Как маппить существующую TURN-авторизацию на OIDC?
8. Один origin на тенант или общий с ACL по библиотекам?
9. Хранить ли выбор на сервере (для кросс-девайс синхронизации) или только локально?
